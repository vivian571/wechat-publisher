【标题】
第七章：路由型指令：针对多功能协作平台（如 Onyx）的精准意图弹射技术

【引言】
想象这样一个真实翻车案例：

某大型电商公司的运营小王，最近在公司内部部署了基于 Onyx 的 AI 知识助手。他本想让 AI “帮我查查去年双十一的退换货周报，顺便分析下今年的库存风险”。

由于 Onyx 这种平台连接了飞书、GitHub、数据库等 50 多个数据源，AI 在接到这个混合指令后，陷入了逻辑混乱。它先是去 GitHub 扫描了前端代码库，认为“周报”是一个代码文件；接着由于无法在代码库里找到库存数据，它开始自作聪明地基于一年前的旧文档编造了一些看似专业的“库存预警”。

最终，小王拿到的不是一份周报，而是一份“结合了业务词汇的赛博科幻小说”。

这种“指令多路冲突”的本质，是因为我们忽略了最关键的一环：路由（Routing）。

【核心原理】
所谓的“路由型指令（Router Prompting）”，其实就是在大语言模型处理具体任务之前，先给它装上一套“意图分拣中心”。

通俗地讲，以前的指令是“把所有快递都拆开看一遍”；而路由型指令则是“先看快递单上的地址，北京的送 A 仓库，上海的送 B 仓库”。

在 Onyx 这种连接了海量数据源的平台上，AI 的智力资源是有限的。如果你不告诉它“先去哪儿查”，它就会因为上下文窗口被无关数据撑满而发生“智降”。路由逻辑的核心本质是：通过先置的意图识别，强制模型在特定的数据域（Domain）内进行深度检索，从而实现精准弹射。

【实战演练】

Level 1：原始指令（低质量）

帮我查查公司最新的报销制度，并看看我上个月提交的那张发票审核进度。

Level 2：优化版本（加入逻辑分发）

你现在是 Onyx 知识枢纽。请分析我的意图。如果是查询“制度”，请去连接飞书文件夹；如果是查询“具体单据”，请去连接报销系统 API。请先告诉我你打算去哪儿查，然后再给出结果。

Level 3：最终工业级路由 Prompt

```markdown
# Role: Onyx Intent Router & Multi-Source Orchestrator

# Working Principles:
1. 在响应任何用户指令前，必须先在内部执行 [Classification_Step]。
2. 你拥有以下 3 个高优先级路由逻辑：
   - Route_A [Knowledge_Base]: 涉及规章、手册、周报。数据源: file:///Users/ax/wechat-publisher/wechat/documents/
   - Route_B [System_Status]: 涉及工单进度、发票审核。数据源: Jira_Api, Invoice_Portal.
   - Route_C [Code_Audit]: 涉及 bug 追踪、版本计划。数据源: GitHub_Repo.

# Decision Forest:
- IF 输入中包含 "进度" OR "订单" -> 执行 Route_B。
- IF 输入中包含 "怎么做" OR "解读" -> 执行 Route_A。
- IF 输入中包含 "代码" OR "库" -> 执行 Route_C。

# Conflict Resolution:
如果用户的意图跨越了两个路由，请拆解为 [Sub_Task_1] 和 [Sub_Task_2] 并行执行，并注明数据源差异。

# Execution Prefix:
你必须以 [Router_Actvated] 作为回复的开头，并明确告知分发路径。
```

【多角度分析】

稳定性：
路由型指令通过提前收窄搜索范围，将模型的“解题空间”压缩到了 1/10。由于无关信息的干扰被物理隔绝，AI 输出逻辑的连贯性会呈现指数级提升，极大地减少了中途“逻辑掉线”的频率。

可扩展性：
当你的平台（如 Onyx）新接入了第 51 个插件或数据源时，你不需要重写整个提示词。你只需要在 Decision Forest（决策森林）里加一行新的路由规则。这种模块化的设计，是支撑大规模 Agent 集群的基础。

抗幻觉能力：
大部分幻觉来自于“信息的张冠李戴”。当路由逻辑锁死了 Route_A 只能在飞书库里找答案时，AI 就没法去 GitHub 里胡编乱造。这种“数据域隔离”是目前对抗长上下文幻觉的最强防线。

【工业级模板】

这是一个标准的路由提示词框架（Router Framework）：

```markdown
# Role: [领域] 分发指挥官

# Environment_Context:
当前平台已集成如下能力：[能力 A, 能力 B, 能力 C...]

# Routing_Logic:
1. 关键词映射（Keywords Mapping）：定义核心动作触发词。
2. 边界判定（Boundaries Check）：明确每个能力的禁区。
3. 兜底策略（Fallback Strategy）：如果意图不明，优先执行哪一个默认动作。

# Output_Protocol:
每一个输出必须包含：
- [Path]: 分发后的执行路径。
- [Confidence]: 意图识别的置信度。
- [Result]: 该路径下的最终输出。
```

逐段解释：
环境上下文建立了 AI 的“自我认知边界”；路由逻辑提供了决策算法，类似于编程中的 if-else；输出协议强制了格式规范，确保后续系统可以解析 AI 的路由决策。

【本章小结】
1. 复杂平台的首要任务不是回答问题，而是分类意图。
2. 路由逻辑必须具备明确的“数据源边界感”。
3. 面对复合指令，要采用“分而治之”的拆解路由。

【练习任务】
请为一个包含“客户支持”和“内部财务审计”的综合型 Agent 平台设计一个双重路由提示词。要求：当用户问“怎么退款”时，自动弹射到 Route_Service；当用户问“上个月利润”时，自动弹射到 Route_Finance。观察在这种引导下，AI 是否还会把退款流程和利润数据搞混。
